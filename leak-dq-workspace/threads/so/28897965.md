## Answer 79836840

responder · Paul Floyd · 2025-12-03T11:51:16Z · score 0 · https://stackoverflow.com/a/79836840

This is an old question. An explanation of the root cause may be useful though.

The problem is with this error report

```
==17917== Invalid write of size 8
==17917==    at 0x5E53E04: __GI_mempcpy (in /usr/lib/libc-2.21.so)

```

That is saying that `mempcpy` is writing to an address in memory that is not on the stack or in an active block of memory allocated on the heap.

Or is it?

The real problem is that functions like `__GI_mempcpy` tend to use SIMD optimisations in order to process multiple bytes in parallel. The code can further exploit the knowledge that memory is always allocated in a multiple of 8 or 16 bytes (depends on the OS). The pointers are 64bit so I will assume allocations in multiples of 16.

Valgrind can't tell apart an error in user code from this deliberate (but safe) error used for optimising string and memory functions. This example is a very good example of that. The first error is an invalid write of size 8 that starts 14 bytes inside a block of size 20. The 20 byte block will really have a size of 32 so writing from bytes 14 to 27 inclusive should be OK. The third error is also a write of size 8, starting 10 bytes after a block of size 20. That means that it is from bytes 30 to 27 inclusive. There is no way that this can be correct.

In order for Valgrind to be able to see only user code errors it replaces all string and memory functions that may perform SIMD optimisations. At the time that this question was written Valgrind wasn't replacing `__GI_mempcpy`. That got fixed in 2015 and was included in the 3.11 release (see [https://bugs.kde.org/show_bug.cgi?id=342795](https://bugs.kde.org/show_bug.cgi?id=342795)).

The error that you should see is something like

```
==1998756== Invalid write of size 1
==1998756==    at 0x404B934: mempcpy (vg_replace_strmem.c:1701)
==1998756==    by 0x407115: test_mempcpy (str_tester.c:1081)
==1998756==    by 0x40859D: main (str_tester.c:1507)
==1998756==  Address 0x3039 is not stack'd, malloc'd or (recently) free'd

```

The key thing here is that you can see the source file (`vg_replace_strmem.c`). That is the file that contains all of the replacements for `str*` and `mem*` (and their wide variants `wcs*` and `wmem*)` libc functions. If you don't see the Valgrind replacement file name for errors of this kind (and only errors of this kind) then it is a sign that Valgrind needs updating. This is most likely to happen if you are using a new version of libc.

Whilst you could use a suppression for this kind of error it is not ideal since it will also mask genuine errors. The best thing to do is to open a bug report at [https://bugs.kde.org](https://bugs.kde.org). This kind of issue is usually fairly easy to remedy and is likely to get fixed quite quickly.
