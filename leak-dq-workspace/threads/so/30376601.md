
## Answer 30403709 [ACCEPTED]

responder · edmz · 2015-05-22T18:38:38Z · score 62 · https://stackoverflow.com/a/30403709

It's Valgrind's fault. First, `-fsanitize=leak` does not show anything. Second, Valgrind itself [states](http://valgrind.org/docs/manual/faq.html#faq.reports) that:

> 
  

First of all: relax, it's probably not a bug, but a feature. Many
  implementations of the C++ standard libraries use their own memory
  pool allocators. Memory for quite a number of destructed objects is
  not immediately freed and given back to the OS, but kept in the
  pool(s) for later re-use. The fact that the pools are not freed at the
  exit of the program cause Valgrind to report this memory as still
  reachable. The behaviour not to free pools at the exit could be called
  a bug of the library though.

  
  

Using GCC, you can force the STL to use malloc and to free memory as
  soon as possible by globally disabling memory caching. Beware! Doing
  so will probably slow down your program, sometimes drastically.

  
  

With GCC 2.91, 2.95, 3.0 and 3.1, compile all source using the STL
  with -D__USE_MALLOC. Beware! This was removed from GCC starting with
  version 3.3.

  
  

With GCC 3.2.2 and later, you should export the environment variable
  GLIBCPP_FORCE_NEW before running your program.

  
  

With GCC 3.4 and later, that variable has changed name to
  GLIBCXX_FORCE_NEW.

  
  

[...]

I guess those alleged memory pools are freed *after* program's termination,  in the so-called start-up code that calls `main`, among the other settings. Internal functions defined outside user's code should be treated as if they didn't exist, that's why Valgrind can't (and shouldn't) see further frees.

## Answer 48362390

responder · Philipp Claßen · 2018-01-21T00:08:05Z · score 8 · https://stackoverflow.com/a/48362390

For gcc 6 and higher, a related bug fix arrived:

- [Bug report: "Warning about "still reachable" memory when using libstdc++ from gcc 5"](https://bugs.kde.org/show_bug.cgi?id=345307)

- [Discussion on the Arch Linux bug tracker](https://bugs.archlinux.org/task/45051)

With gcc 5, you can also get the same warning without including `iostream`.

So, if you see a similar warning referring to `dl-init.c` and you are using gcc 5, consider upgrading to a newer version (gcc >=6), or try to compile with clang.

(the above requires the use of `--run-cxx-freeres=no` to prevent the memory block from being deallocated and for memcheck to report the block as still reachable).

All of that 'eh_alloc' stuff is allocating memory for exception handling. It is fairly tricky to free that memory - you would need to be certain that there is zero possibility of an exception being thrown after the memory is freed. That source is part of libstdc++, a component of GCC. The GCC developers decided that it was simpler and safer to not free that memory and to leave it deliberately "still reachable". That's not unreasonable for a relatively small allocation that is bounded - the allocation only happens once during startup.

Whilst it is tricky for libstdc++ to clean up its exception handling memory it is more easily done within Valgrind. Memcheck keeps on running after the guest exe has exited. With GCC 6 and later libstdc++ provides a cleanup function, `__gnu_cxx::__freeres()`. libsctd++ doesn't call this itself, it is meant for tools like Valgrind. After the last guest thread finishes Valgrind executes a function that will call the libstdc++ freeres function (and also one in GNU libc for platforms using that). That frees the memory and Valgrind does not report the memory as still reachable.

This was added to Valgrind back in 2016.
