## Answer 33174997 [ACCEPTED]

responder · Surt · 2015-10-16T16:10:33Z · score 5 · https://stackoverflow.com/a/33174997

According to the [man](http://man7.org/linux/man-pages/man2/mmap.2.html) and under `unmap`:

> 
  

The region is also automatically unmapped when the process is
  terminated.

Which sounds very reasonable as the memory is added to the processes pages in the virtual memory which is freed upon termination.

[Opengroup](http://pubs.opengroup.org/onlinepubs/9699919799/functions/mmap.html) doesn't say anything on the subject.

If the system does not free the memory You can try to set an at_exit up to clear up any still allocated memmaps that are still valid if you can find a pointer to it.

## Answer 62286747

responder · user1564286 · 2020-06-09T15:57:45Z · score 1 · https://stackoverflow.com/a/62286747

I just found out the hard way, that *mmap()* without *munmap()* also causes a leak if the process **isn't** terminated, but just keeps on running.
In hindsight, that seems pretty evident.

While investigating a memory leak for days on end, I now realize that I shouldn't have relied entirely on Valgrind to find the cause. I was dumbfounded when Valgrind reported no leak at all, while I could just see the VSZ section of the *ps* report about my process increasing steadily.

Then after desperately Googling further, ultimately a remark [here](https://utcc.utoronto.ca/~cks/space/blog/linux/LinuxMemoryStats) put me on the right track :

> 
  

If your program is in a steady state but your VSZ keeps increasing, you have some sort of allocation leak. It may not strictly be a memory leak; you might be forgetting to unmap files or unload dynamically loaded code or something.

And as stated clearly in [this SO topic](https://stackoverflow.com/questions/28251833/mmap-and-valgrind-mmap-doesnt-increase-heap-size), Valgrind does NOT report *mmap()* leaks.
