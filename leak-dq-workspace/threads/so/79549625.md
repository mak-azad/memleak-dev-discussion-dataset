## Answer 79586983

responder · John Bollinger · 2025-04-22T16:05:55Z · score 1 · https://stackoverflow.com/a/79586983

@mevets pointed to the issue in [their answer](https://stackoverflow.com/a/79549723/2402272), but I'll be a little more definitive.

You have function `startPiperThread()` to start a new thread and provide data about it, and a function `endPiperThread()` to orchestrate a shutdown of such a thread and clean up the data structures allocated for its use.  These must be called by a thread different from the one being managed.

The implementation of `endPiperThread()` demonstrates a misunderstanding of the function and use of the `pthread_join()` and `pthread_exit()` functions.  The code suggests that you think `pthread_exit()` causes a thread specified by its argument to exit, but this is not the case.  Instead, it causes *the thread that calls it* to exit.  The argument is then made available to whatever thread, if any, successfully joins the exited thread.  `pthread_exit()` always succeeds, so, to a first approximation, no further code runs in a thread that calls it.  That means none of the cleanup code in your `endPiperThread()` runs.

As for `pthread_join()`, this function does not return successfully until the thread designated by its first argument has terminated. Therefore, once you call `pthread_join()` for the managed thread, it's largely out of the caller's hands anyway.  With a few caveats, the caller has no opportunity to do anything further to induce the managed thread to terminate, because it is blocked until that termination happens.

Overall: **remove the `pthread_exit()` call from `endPiperThread()`.**  It is neither needed nor appropriate.
