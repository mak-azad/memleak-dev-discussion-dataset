## Answer 7955193

responder · onemasse · 2011-10-31T14:36:50Z · score 3 · https://stackoverflow.com/a/7955193

The man page for dlclose doesn't say anything about freeing memory when it's called.

```
dlclose()
   The  function  dlclose()  decrements the reference count on the dynamic
   library handle handle.  If the reference count drops  to  zero  and  no
   other  loaded  libraries use symbols in it, then the dynamic library is
   unloaded.

   The function dlclose() returns 0 on success, and nonzero on error.

```

No magic.

If you're using linux you could try [this method](http://www.gnu.org/s/hello/manual/libc/Hooks-for-Malloc.html) to wrap malloc() and keep track of the allocated memory.

## Answer 7955222

responder · cyco130 · 2011-10-31T14:39:12Z · score 5 · https://stackoverflow.com/a/7955222

`dlclose` doesn't free memory allocated with `malloc`. It only frees the static variables declared in the library. You should explicitly free any allocated memory in your library, possibly in the `_fini` function.

## Comment on question 7955109 9724672

responder · jim mcnamara · 2011-10-31T14:58:28Z · score 0 · https://stackoverflow.com/questions/7955109/#comment9724672_7955109

You've essentially answered your own question - the behavior is that you call dlopen once per library or get memory leaks. The only exception I know of is the case (used it in Solaris) of calling exec with and with an earlier fcntl() call on the the file handle for dlopen (handle == a file descriptor) with FC_CLOEXEC set. After the call the child process no longer has an open handle. There is no need to call dlopen repeatedly. Period.  Do you know about dlsym() to get entry points for functions - that you can call over and over again.
