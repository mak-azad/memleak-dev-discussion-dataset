## Question

I have the following case:

```
boost::ptr_vector<float> vec;

float* array = new float[4]();
vec.push_back(array);

// Add some more elements to vec..

```

How can I ensure that if I leave this scope and vec will be destroyed the ptr_vector's destructor calls `delete[]` and not `delete` on every element of `vec`. I don't understand how it should work, because the template parameter float will be the same for `float*` and `float[4]`.

## Answer 9327103 [ACCEPTED]

responder · Steve Jessop · 2012-02-17T11:06:02Z · score 3 · https://stackoverflow.com/a/9327103

You could specify the `CloneAllocator` template parameter of `ptr_vector` to be something other than the default, `heap_clone_allocator`. There is no way to make an instance of the actual class `boost::ptr_vector<float>` use `delete[]` instead of `delete`.

responder · Steve Jessop · 2012-02-17T11:22:08Z · score 2 · https://stackoverflow.com/questions/9327003/#comment11769156_9327103

@morph: I don't think Boost provides one to fit this case, so write your own Clone Allocator. Presumably the reason they don't provide one is that they don't think a `ptr_vector` containing pointers to C arrays is very useful -- it's somewhat ugly in that the ptr_vector accessors give you references only to the first element of each array. I guess you end up writing `(&my_vector[0])[1]`, maintaining a separate container with the sizes, and other such nastiness. If the arrays are all size 4, then use a `vector` or `ptr_vector` of `boost::array<float,4>`.

## Comment on answer 9327102 11770472

responder · Mike Seymour · 2012-02-17T12:33:16Z · score 2 · https://stackoverflow.com/questions/9327003/#comment11770472_9327102

@pavelkolodin: Consider an implementation where the array form stores the size of the allocation, and the single-object form infers it from the object size. Incorrectly calling `delete` will infer the wrong size, so large blocks of memory might be wasted; incorrectly calling `delete[]` will read an invalid size, which could make almost anything happen. That's just one example of an implementation that could go wrong if you try to rely on your guesses about undefined behaviour.
